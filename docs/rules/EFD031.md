# EFD031: LINQ composed over a stored-procedure call

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD031 when a LINQ operator is composed over `FromSqlRaw`, `FromSql`, or `FromSqlInterpolated`, and the SQL starts with `EXEC`, `EXECUTE`, or `CALL`.

To compose LINQ over raw SQL, EF Core wraps the SQL in a subquery: `SELECT … FROM (your SQL) AS o WHERE …`. A stored-procedure call can't be wrapped that way, so the query throws "FromSqlRaw or FromSqlInterpolated was called with non-composable SQL and with a query composing over it" when it executes. The code compiles, and the failure appears only at runtime.

## Reported shapes

```csharp
// Before: throws, because EF Core can't add the WHERE around the procedure call.
var open = context.Orders
    .FromSqlRaw("EXEC dbo.GetOrders @p0", customerId)
    .Where(order => order.Open)
    .ToList();

// After: materialize the procedure's rows, then filter on the client.
var open = context.Orders
    .FromSqlRaw("EXEC dbo.GetOrders @p0", customerId)
    .AsEnumerable()
    .Where(order => order.Open)
    .ToList();
```

Any operator that EF Core would add to the SQL is reported:

- `Queryable` operators such as `Where`, `Select`, `OrderBy`, `Skip`, `Take`, `First`, `Single`, `Count`, and `Any`;
- `Include` and `ThenInclude`;
- async terminals such as `FirstOrDefaultAsync`, `CountAsync`, and `AnyAsync`.

Between the call and the operator, EFD031 looks through `AsNoTracking`, `AsTracking`, `IgnoreQueryFilters`, `TagWith`, and query locals whose value is statically determined. It reports only the first composing operator. The SQL keyword is read from a constant string, or from the literal text an interpolated string starts with.

## Boundaries

EFD031 doesn't report:

- a result that is materialized directly: `ToList()`, `ToArray()`, `ToListAsync()`, `AsEnumerable()`, `AsAsyncEnumerable()`, `LoadAsync()`, or `foreach`;
- composition after `AsEnumerable()` or `ToList()`, which runs on the client;
- composable SQL, such as `SELECT * FROM dbo.GetOrdersFn(@p0)`, or any SQL that doesn't start with `EXEC`, `EXECUTE`, or `CALL`. A procedure name used without `EXEC` is outside the rule, because it can't be told apart from a table or view name;
- SQL text the analyzer can't read, such as a parameter, a field, or a method result.

## Remediation

- When the procedure's result is small, materialize it first with `AsEnumerable()` or `ToList()`, and compose on the client.
- When the database should do the filtering, replace the procedure with a table-valued function or a view, and query it with `FromSql($"SELECT * FROM dbo.GetOrdersFn({customerId})")`. EF Core can compose over that. You can also map the function with `HasDbFunction`, and query it directly.

## Suppression

Suppress only when your provider composes procedure output, and record which provider.

```csharp
[SuppressMessage("Correctness", "EFD031", Justification = "Legacy provider composes procedure output.")]
static List<Order> Open(SampleContext context) => ...;
```

`#pragma warning disable EFD031` and `dotnet_diagnostic.EFD031.severity = none` in `.editorconfig` also work.
