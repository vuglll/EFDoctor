# EFD035: Unsized column in the model snapshot

**Default severity:** Warning (high-confidence findings), suggestion (advisory findings)

**Confidence:** High for an indexed unbounded string, Advisory for a defaulted decimal

EFDoctor reports EFD035 for two SQL Server column types in the EF Core model snapshot that cause real failures, and that you can usually see only there.

## An index or key on `nvarchar(max)`

A `string` property with no maximum length maps to `nvarchar(max)`, or `varchar(max)` for non-Unicode strings. SQL Server can't use those types as index key columns, so the migration that creates an index or key on one fails when it is applied:

```csharp
// Snapshot: reported with high confidence.
b.Property<string>("Email").HasColumnType("nvarchar(max)");
b.HasIndex("Email");
```

Fix it in the model with `HasMaxLength(256)` or `[MaxLength(256)]`, then generate a migration. An index key on SQL Server can be at most 1700 bytes, or 850 `nvarchar` characters. If the column really must be unbounded, index a computed hash or prefix column instead.

EFD035 reports the property when its name is any column of a `HasIndex`, `HasKey`, or `HasAlternateKey` of the same entity in the snapshot. Unbounded strings that aren't indexed aren't reported, because long text and encrypted payloads are often unbounded on purpose.

## A `decimal` left at `decimal(18,2)`

When the model doesn't configure a decimal's precision, EF Core falls back to SQL Server's `decimal(18,2)`, and logs a warning that values may be "silently truncated". A rate, a percentage, or a unit price with more than two decimal places is rounded when it is saved:

```csharp
// Snapshot: reported with advisory confidence.
b.Property<decimal>("TaxRate").HasColumnType("decimal(18,2)");

// Model: configure the precision the values need.
builder.Property(i => i.TaxRate).HasPrecision(9, 6);
```

EFD035 reports a `decimal` or `decimal?` property whose snapshot type is exactly `decimal(18,2)` with no `HasPrecision`. It doesn't report one whose CLR property in the project has `[Precision]`, or `[Column(TypeName = …)]`. The finding is advisory, because an explicit `HasColumnType("decimal(18,2)")` in fluent configuration in another file looks the same in the snapshot. Suppress it in that case.

## Boundaries

- Only SQL Server store types are checked. PostgreSQL's `text` and `numeric`, and SQLite's types, aren't reported.
- Decimals with any other store type, or with `HasPrecision`, aren't reported.
- The snapshot must be in the analyzed project. Findings point to the snapshot's `Property(…)` chain, so fix the model and regenerate the snapshot, rather than editing the snapshot.

## Suppression

Snapshots are generated, so the clearest suppression is `.editorconfig` scoped to the snapshot file, with a recorded reason:

```ini
[Migrations/ShopContextModelSnapshot.cs]
# Reviewed: decimal(18,2) is configured with HasColumnType in OrderConfiguration.
dotnet_diagnostic.EFD035.severity = none
```

`#pragma warning disable EFD035` around the property also works.
