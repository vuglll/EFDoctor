# EFD015: Materialized key list used in another query's Contains

**Default severity:** Info

**Confidence:** Advisory

EFDoctor reports EFD015 when an EF Core query filters with `list.Contains(x.Column)`, and `list` was loaded from another query only for that purpose: with `ToList()`, `ToArray()`, or `ToHashSet()` on the same `DbContext`, from a query with no `Take` or key bound.

That two-step shape costs a round trip, and its size has no bound. The first query brings every matching value to the client, and the second sends them all back. EF Core sends the list as a JSON parameter since version 8, which the optimizer can't estimate. Older versions inline it as constants, one query plan per list. Keeping the first query as an `IQueryable` lets EF Core compose one statement, `WHERE CustomerId IN (SELECT Id FROM Customers WHERE …)`, and the database does the work in one trip.

## Reported shapes

```csharp
// Before: the keys travel to the client and back.
var customerIds = await context.Customers
    .Where(c => c.Region == region)
    .Select(c => c.Id)
    .ToListAsync();
var orders = await context.Orders.Where(o => customerIds.Contains(o.CustomerId)).ToListAsync();

// After: one statement, with a subquery.
var customerIds = context.Customers.Where(c => c.Region == region).Select(c => c.Id);
var orders = await context.Orders.Where(o => customerIds.Contains(o.CustomerId)).ToListAsync();
```

The `Contains` can be an instance call or `Enumerable.Contains(list, value)`. It can be in any `Queryable` operator's lambda, including a nested lambda over a navigation. The awaited `ToListAsync`, `ToArrayAsync`, and `ToHashSetAsync` count as loads. The diagnostic points to the `Contains` call. The evidence names the local and the query that loaded it.

## Boundaries

EFD015 doesn't report:

- an inner query with `Take`, or a key equality, whose list is small by construction;
- a list the method uses for anything else, such as `Count`, a `foreach`, a return, or a method argument, where the materialization is needed anyway;
- a list built in memory, passed in as a parameter, or held in a field;
- an inner query on a different `DbContext` instance, where a subquery isn't possible;
- a `Contains` over an in-memory sequence, or one whose tested value doesn't read the query's entity.

## Remediation

- Remove the `ToList()`/`ToListAsync()` from the inner query, so it stays an `IQueryable` and EF Core composes it as a subquery.
- Or express the filter as a join or a navigation: `context.Orders.Where(o => o.Customer.Region == region)`.
- Keep the list when it is small and known to stay small, or when it is reused.

## Suppression

```csharp
[SuppressMessage("Performance", "EFD015", Justification = "Regions is capped at a few dozen rows.")]
```

To turn the advisory rule off for a project, set `dotnet_diagnostic.EFD015.severity = none` in `.editorconfig`. `#pragma warning disable EFD015` works too.
