# EFD006: Multiple sibling collection includes may create a cartesian explosion

**Default severity:** Warning

**Confidence:** Medium

EFDoctor reports EFD006 when semantic analysis proves that one inline EF Core query contains at least two distinct root-level collection `Include` paths and no explicit `AsSplitQuery`.

When sibling collections are loaded with joins in one SQL query, each row from one collection can be combined with each row from the other. The result may multiply rows and duplicate principal columns, increasing database work, network transfer, and EF materialization cost. EFD006 identifies a risky query shape; it does not measure cardinality or prove that a particular query is slow.

## Reported shape

```csharp
var blogs = context.Blogs
    .Include(blog => blog.Posts)
    .Include(blog => blog.Contributors);
```

The diagnostic points to the complete `Include` invocation that introduces the second distinct collection. Evidence lists every distinct sibling collection path observed in the inline chain. Filtered collection includes still count:

```csharp
var blogs = context.Blogs
    .Include(blog => blog.Posts.Where(post => post.Published))
    .Include(blog => blog.Contributors.OrderBy(person => person.Name));
```

## Semantic and expression boundaries

Calls must resolve to EF Core `EntityFrameworkQueryableExtensions.Include`, and the inline source must trace through resolved `Queryable` and EF composition to `DbSet<T>` or `DbContext.Set<TEntity>()`. Static and extension syntax are supported. Method-name text, string-based includes, unrelated methods, in-memory queries, and arbitrary `IQueryable<T>` values are insufficient.

The first version counts only distinct collection properties selected by root-level `Include` calls. It does not report:

- one collection include by itself;
- reference navigation includes;
- the same collection path repeated;
- collection paths that occur only beneath one `ThenInclude` branch; or
- query composition that would require following a field, property, parameter, return value, helper, or a local whose value isn't statically determined.

Includes split across a query local whose value is statically determined (see [query locals](README.md#query-locals)) are combined, and the finding is reported once. It's at the second distinct collection include, whether that include is written before the local or after it.

This narrow boundary favors explainable findings over speculative navigation-tree analysis.

## Split-query behavior

An explicit, resolved `AsSplitQuery` or `AsSingleQuery` anywhere in the same inline chain prevents EFD006. `AsSplitQuery` makes EF Core load the included collections with separate SQL queries. `AsSingleQuery` records a deliberate choice of single-query loading, for example to get a consistent snapshot. EF Core itself only warns about multiple collection includes when neither mode is chosen. A global `UseQuerySplittingBehavior` configuration isn't followed, so suppress with a recorded reason when you rely on it.

EFDoctor does not inspect global `UseQuerySplittingBehavior` configuration. If split-query behavior is configured outside the expression, review and suppress the finding with that specific reason. Conversely, do not add `AsSplitQuery` mechanically: split queries add database round trips and can observe inconsistent results when concurrent updates occur unless the transaction isolation level provides the required consistency.

## Remediation

Inspect the generated SQL and expected collection cardinalities first. Depending on the query's intent, consider:

- `AsSplitQuery` after evaluating round-trip and consistency trade-offs;
- a projection that selects only the required columns and shapes;
- separate targeted queries; or
- leaving the single query intact when cardinalities are known to be small and measured behavior is acceptable.

## Suppression

Use standard Roslyn suppression and record why the single-query shape is intentional or why split-query behavior is configured elsewhere.

```csharp
#pragma warning disable EFD006 // Reviewed: global split-query behavior applies to this context.
var blogs = context.Blogs
    .Include(blog => blog.Posts)
    .Include(blog => blog.Contributors);
#pragma warning restore EFD006
```

For a file or directory scope in `.editorconfig`:

```ini
[ReadModels.cs]
# Reviewed: these known-small read models intentionally use one query.
dotnet_diagnostic.EFD006.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Performance",
    "EFD006",
    Justification = "Global split-query behavior applies to this context.")]
IQueryable<Blog> LoadBlogs(BloggingContext context) =>
    context.Blogs
        .Include(blog => blog.Posts)
        .Include(blog => blog.Contributors);
```
