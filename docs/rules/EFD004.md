# EFD004: Query is materialized before SQL-capable composition

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD004 when semantic analysis proves that an EF Core query is materialized with `ToList`, `ToArray`, `ToListAsync`, or `ToArrayAsync` and the buffered result is immediately filtered, projected, ordered, or paged with a conservatively supported LINQ-to-Objects expression.

Early materialization can transfer and buffer more rows or columns than needed and prevents the later supported operation from being composed into SQL. This is a review prompt, not a claim that every occurrence is wrong, that every result is large, or that rewriting it guarantees a measurable improvement.

## Reported forms

EFD004 covers an immediate `Enumerable.Where`, `Select`, `OrderBy`, `OrderByDescending`, `Skip`, or `Take` after materialization:

```csharp
// Before: filtering happens after rows are buffered.
var active = context.Customers.ToList().Where(customer => customer.Active);

// After: filtering can be composed into SQL.
var active = context.Customers.Where(customer => customer.Active).ToList();
```

Awaited asynchronous materializers are supported:

```csharp
// Before
var names = (await context.Customers.ToArrayAsync(cancellationToken))
    .Select(customer => customer.Name);

// Review-preserving rewrite
var names = await context.Customers
    .Select(customer => customer.Name)
    .ToArrayAsync(cancellationToken);
```

The diagnostic points to the complete materializer invocation. Evidence identifies the resolved materializer, the proven `DbSet` origin, and the immediate client-side operator.

## Semantic and expression boundaries

Synchronous materializers must resolve to `System.Linq.Enumerable.ToList` or `ToArray`. Asynchronous materializers must resolve to EF Core `EntityFrameworkQueryableExtensions.ToListAsync` or `ToArrayAsync`. In every case, EFDoctor traces the inline source through resolved `Queryable` and EF composition back to a `DbSet` or `DbContext.Set<TEntity>()`; method-name text and arbitrary `IQueryable<T>` values are insufficient.

The first version accepts deliberately narrow downstream shapes:

- `Where` with direct entity property paths, constants, captured locals or parameters, null checks, built-in comparisons, and `&&`, `||`, or `!` combinations;
- `Select` of a direct property path or an anonymous object made from supported properties and scalar values;
- `OrderBy` or `OrderByDescending` with a direct property path; and
- `Skip` or `Take` with an integral literal, parameter, or captured local.

EFD004 does not report arbitrary method calls, computed members, indexed lambdas, dynamic expressions, assignments, user-defined operators, unrelated or unresolved methods, or in-memory collections. It also respects explicit `AsEnumerable` and `AsAsyncEnumerable` client-evaluation boundaries.

The query before the materializer may be stored in a local whose value is statically determined (see [query locals](README.md#query-locals)). The materialized value itself is not followed: EFDoctor does not follow it through a local, field, property, return value, argument, helper, or general data flow:

```csharp
var customers = context.Customers.ToList();
return customers.Where(customer => customer.Active); // Not reported in the first version.
```

An unsupported immediate operation prevents a finding even when a supported operation appears later in the same chain. These boundaries prioritize explainable, high-confidence findings over broad provider-dependent guesses.

## Remediation and legitimate exceptions

Consider moving the supported operation before materialization, preserve cancellation and ordering behavior, and inspect generated SQL. Projection changes deserve particular care because moving `Select` can change entity materialization and tracking semantics.

Keeping the client-side operation can be intentional when the result is known to be small and bounded, client-only logic is required, buffered values are reused, the provider cannot translate the desired expression, or tracking and semantic requirements depend on the materialization boundary. Record that reason when suppressing the diagnostic.

## Suppression

Use standard Roslyn suppression; EFDoctor has no proprietary suppression file.

For the smallest source region:

```csharp
#pragma warning disable EFD004 // Reviewed: bounded results are reused by client-only processing.
var result = context.Customers.ToList().Where(customer => customer.IsActive);
#pragma warning restore EFD004
```

For a file or directory scope in `.editorconfig`:

```ini
[BoundedClientQueries.cs]
# Reviewed: this file intentionally processes small cached lookup sets in memory.
dotnet_diagnostic.EFD004.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Performance",
    "EFD004",
    Justification = "Provider translation limitation; the bounded result is intentionally filtered client-side.")]
IEnumerable<Customer> FilterOnClient(DbContext context)
{
    return context.Set<Customer>().ToList().Where(customer => customer.IsActive);
}
```
