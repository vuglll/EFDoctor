# EFD012: Dynamic SQL passed to an EF Core raw-SQL API

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD012 when semantic analysis proves that dynamically constructed SQL text is passed to EF Core `FromSqlRaw`, `ExecuteSqlRaw`, or `ExecuteSqlRawAsync`. Interpolation and non-constant concatenation can place values directly into SQL text, which can permit SQL injection and can produce a different query text—and therefore a different cached plan—for each value. The finding proves the code shape; it does not prove that an input is attacker-controlled, that an exploit exists, or that plan-cache cost was measured.

## Reported shapes

```csharp
var customers = context.Customers
    .FromSqlRaw($"SELECT * FROM Customers WHERE Id = {id}");

context.Database.ExecuteSqlRaw(
    "DELETE FROM Customers WHERE Name = '" + name + "'");
```

The first version also follows a uniquely assigned local in the same straight-line block:

```csharp
var sql = $"SELECT * FROM Customers WHERE Id = {id}";
var customers = context.Customers.FromSqlRaw(sql);
```

The diagnostic spans the SQL argument at the raw call. For a local origin, that means the local identifier; the evidence identifies the upstream interpolation or concatenation and names the resolved EF Core operation.

## Non-triggering safe forms

Pass values separately from constant raw SQL:

```csharp
var customers = context.Customers.FromSqlRaw(
    "SELECT * FROM Customers WHERE Id = {0}",
    id);
```

Or use an EF Core API that accepts an interpolated SQL value and converts holes to parameters:

```csharp
var customers = context.Customers
    .FromSqlInterpolated($"SELECT * FROM Customers WHERE Id = {id}");

await context.Database.ExecuteSqlInterpolatedAsync(
    $"DELETE FROM Customers WHERE Id = {id}");
```

Constant SQL, compile-time constant concatenation, unrelated same-named methods, unknown SQL parameters, and raw values whose unsafe origin cannot be proved do not report.

## Semantic and data-flow boundaries

The invocation must resolve to the supported methods on EF Core's relational extension types. Reduced extension and static invocation syntax are supported; matching source text alone is insufficient.

Local-origin analysis is intentionally conservative. It follows a local only when exactly one initializer or assignment precedes the call in the same operation block. Multiple assignments, conditional or loop-controlled writes, fields, properties, parameters, return values, helper methods, and cross-method flow are not reported by the first version. This boundary favors high-confidence evidence over broad taint inference.

## Remediation

Use placeholders with separate value arguments or an interpolated-safe EF Core API. Do not try to parameterize SQL identifiers or structural fragments such as table names, column names, sort directions, or complete clauses: database value parameters cannot represent those. If structure must vary, select it from an explicit fixed allow-list and keep all data values parameterized.

## Suppression

Use standard Roslyn suppression only after verifying that every dynamic structural fragment comes from a fixed allow-list, then record that reason.

```csharp
#pragma warning disable EFD012 // Reviewed: fragment is selected from a fixed allow-list.
context.Database.ExecuteSqlRaw("DELETE FROM Customers " + allowedClause);
#pragma warning restore EFD012
```

For a file or directory scope in `.editorconfig`:

```ini
[AllowListedMaintenanceSql.cs]
# Reviewed: every identifier and clause is selected from a fixed allow-list.
dotnet_diagnostic.EFD012.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Security",
    "EFD012",
    Justification = "Every structural fragment is selected from a fixed allow-list.")]
int ExecuteMaintenance(DatabaseFacade database, string allowedClause) =>
    database.ExecuteSqlRaw("DELETE FROM Customers " + allowedClause);
```
