# EFD033: DbContext captured by a singleton

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD033 when a service is registered as a singleton, with `AddSingleton`, `TryAddSingleton`, or `AddHostedService`, and either of these holds:

- every public constructor of its implementation takes a `DbContext`;
- its factory resolves a `DbContext` from the root service provider.

`AddDbContext` registers a context as **scoped**: one instance per request or scope. A singleton lives for the whole application, so a singleton that takes the context keeps one instance forever:

- With scope validation on, the default in the Development environment, the host fails to start ("Cannot consume scoped service … from singleton …").
- In Production, scope validation is off, so the app starts. Every request then shares one `DbContext`. A context isn't thread-safe, so concurrent requests throw "A second operation was started on this context instance". Tracked entities go stale, and the change tracker grows without bound.

## Reported shapes

```csharp
services.AddDbContext<ShopContext>(...);

// Reported: PriceCache(ShopContext db) is a singleton.
services.AddSingleton<IPriceCache, PriceCache>();

// Reported: hosted services are singletons. CleanupWorker(ShopContext db).
services.AddHostedService<CleanupWorker>();

// Reported: the factory resolves the context from the root provider.
services.AddSingleton<IPriceCache>(sp => new PriceCache(sp.GetRequiredService<ShopContext>()));
```

`typeof` registrations (`AddSingleton(typeof(IPriceCache), typeof(PriceCache))`) and `TryAddSingleton` are reported the same way. The diagnostic points to the registration. The evidence names the implementation and the constructor parameter, or the factory's resolution.

## Boundaries

EFD033 doesn't report:

- the correct patterns: a singleton that takes `IDbContextFactory<T>`, `IServiceScopeFactory`, or `IServiceProvider`, or a factory that resolves the context from a scope it creates;
- `AddScoped` or `AddTransient` registrations;
- an implementation with another public constructor that takes no `DbContext`, because the analyzer can't tell which one the container uses;
- a context the same project registers as a singleton, for example `AddDbContext<T>(…, ServiceLifetime.Singleton)`. A singleton consumer is then consistent with it, although a singleton context has the same sharing problems;
- an implementation type declared in a referenced assembly, registrations made through assembly scanning or a third-party container, and transitive captures, such as a singleton that takes a scoped repository that takes the context.

## Remediation

- Take `IDbContextFactory<TContext>`, registered with `AddDbContextFactory`, and create a short-lived context per operation with `await using var db = await factory.CreateDbContextAsync();`.
- Or take `IServiceScopeFactory`, and resolve the context inside a scope per unit of work. This is the usual pattern in hosted services.
- Or register the service as scoped, if it doesn't need to be a singleton.

## Suppression

Suppress only when the singleton provably runs on one thread and uses the context briefly, such as in a single-threaded console tool, and record why.

```csharp
[SuppressMessage("Reliability", "EFD033", Justification = "Single-threaded import tool.")]
static void RegisterImportTool(IServiceCollection services) => services.AddSingleton<Importer>();
```

`#pragma warning disable EFD033` and `dotnet_diagnostic.EFD033.severity = none` in `.editorconfig` also work.
