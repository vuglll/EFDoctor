# EFD025: Include path is redundant with another Include in the same query

**Default severity:** Info

**Confidence:** High

**Category:** Maintainability

EFDoctor reports EFD025 when semantic analysis proves that an inline EF Core query contains an `Include` chain that another chain in the same query makes redundant. An include chain is one `Include` plus any `ThenInclude` calls that continue it. A chain is redundant in two cases:

- **Duplicate:** an earlier chain in the query has exactly the same navigation path.
- **Covered prefix:** a longer chain in the query, before or after it, starts with the same path. EF Core loads every navigation along a path, so the shorter chain adds nothing.

EF Core merges every include path in a query, so a redundant chain changes neither the generated SQL nor the loaded data. The cost is misleading query intent. Readers assume the loading shape is more complex than it is, and the leftover call is easy to miss when the other path changes. EFD025 is a cleanup rule, so it reports at `Info` severity.

## Reported shapes

```csharp
// Duplicate: the second Include(order => order.Customer) is reported.
context.Orders
    .Include(order => order.Customer)
    .Include(order => order.Customer);

// Covered prefix: the bare Include(order => order.Lines) is reported,
// because Lines.Product already loads Lines.
context.Orders
    .Include(order => order.Lines)
    .Include(order => order.Lines).ThenInclude(line => line.Product);

// Nested member path: Include(blog => blog.Owner) is covered by Owner.Address.
context.Blogs
    .Include(blog => blog.Owner)
    .Include(blog => blog.Owner.Address);

// Constant string paths are compared with each other.
context.Orders
    .Include("Customer.Address")
    .Include("Customer.Address");
```

Each redundant chain produces one finding. The finding location runs from the redundant `Include` through the chain's last `ThenInclude`, and leaves out the query receiver. With static extension syntax (`EntityFrameworkQueryableExtensions.Include(...)`), the location is the chain's outermost call. The evidence names the proven `DbSet` origin, the redundant path, the path that duplicates or covers it, and the reason. Expression paths are shown as `'Order.Lines.Product'` and string paths as `"Customer.Address"`.

The earliest occurrence of every longest path is never reported. So you can delete every reported chain and the query still loads the same navigations.

The query can use supported composition between the includes: `Where`, ordering, `Skip`, `Take`, `Distinct`, tracking modes, `AsSplitQuery`/`AsSingleQuery`, `IgnoreQueryFilters`, `IgnoreAutoIncludes`, and tags. A chain that ends in a materializer or `Select`, such as `.ToList()` or `.FirstOrDefaultAsync()`, is analyzed once.

## Not reported

Branching into different `ThenInclude` continuations needs a repeated leading `Include`. That repetition is required syntax, so it is not reported:

```csharp
context.Orders
    .Include(order => order.Lines).ThenInclude(line => line.Product)
    .Include(order => order.Lines).ThenInclude(line => line.Warehouse);
```

EFD025 also stays silent when it can't prove two chains are equivalent. A chain that contains any of the following takes part in no comparison:

- a filtered include, such as `Include(order => order.Lines.Where(line => line.Quantity > 0))`, or a filtered `ThenInclude`. This applies even next to an identical filter or an unfiltered include of the same navigation.
- a cast or other selector that isn't a plain property path rooted at the lambda parameter, such as `Include(blog => ((Blog)blog).Posts)`.
- a non-constant string path, or a string path with an empty segment.

A string path is compared only with other string paths. `Include("Customer")` next to `Include(order => order.Customer)` is not reported, because mapping a string to a CLR property needs the runtime EF model. Paths are compared by resolved property, not by name, so `Owner.Address` and `Sponsor.Address` never match.

## Semantic and inline-flow boundaries

`Include` and `ThenInclude` must resolve to `EntityFrameworkQueryableExtensions`, and the chain must trace to `DbSet<T>` or `DbContext.Set<TEntity>()`. EFD025 does not report look-alike methods with the same names, in-memory `AsQueryable()` sources, or arbitrary `IQueryable<T>` parameters.

EFD025 compares includes within one directly connected invocation chain, including through query locals whose value is statically determined (see [query locals](README.md#query-locals)). Each finding is reported once, at the redundant include. It does not report when:

- includes are split across a field, property, parameter, or conditional query-building step (`if (x) query = query.Include(...)`)
- a helper or custom query operator sits between the includes
- a `Select`, grouping, join, or other element-type-changing operator appears in the chain
- a navigation is also configured with `AutoInclude()` in the EF model, because EFDoctor does not read model configuration

## Remediation

Delete the redundant `Include`/`ThenInclude` chain. The query still loads the same navigations through the other path.

## Suppression

If you keep a redundant include on purpose, for example to document intent, use standard Roslyn suppression and record the reason.

```csharp
#pragma warning disable EFD025 // Reviewed: the repeated include mirrors a generated query template.
var orders = context.Orders
    .Include(order => order.Customer)
    .Include(order => order.Customer);
#pragma warning restore EFD025
```

For a file or directory scope, or to turn the rule off entirely, use `.editorconfig`:

```ini
[EditorConfigSuppressed.cs]
# Reviewed: the repeated include mirrors a generated query template kept in sync by hand.
dotnet_diagnostic.EFD025.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Maintainability",
    "EFD025",
    Justification = "The repeated include mirrors a generated query template.")]
IQueryable<Order> Load(SampleContext context) =>
    context.Orders
        .Include(order => order.Customer)
        .Include(order => order.Customer);
```

An unsuppressed EFD025 finding counts toward exit code `1`, like every other finding.
