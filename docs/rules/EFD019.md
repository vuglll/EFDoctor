# EFD019: Query is materialized and then immediately reduced

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD019 when semantic analysis proves that an EF Core query is materialized with `ToList`, `ToArray`, or an awaited `ToListAsync`/`ToArrayAsync`, and the buffered result is immediately reduced to a single element, a count, a boolean, or an aggregate.

Materializing first transfers and buffers every row the query returns, and tracks them for entity queries, only to discard almost all of them on the client. The database could compute the same result and return one row or one value. The cost grows with the number of rows the query returns, so the shape often looks fine in development and becomes expensive in production.

## Reported shapes

```csharp
// Before: every invoice is loaded to find one.
var invoice = context.Invoices.ToList().FirstOrDefault(invoice => invoice.Id == id);

// After: the database returns at most one row.
var invoice = context.Invoices.FirstOrDefault(invoice => invoice.Id == id);
```

```csharp
// Before: every unpaid invoice is loaded to count them.
var unpaid = (await context.Invoices.Where(invoice => !invoice.Paid).ToListAsync()).Count;

// After
var unpaid = await context.Invoices.Where(invoice => !invoice.Paid).CountAsync();
```

```csharp
// Before
var total = context.Invoices.ToArray().Sum(invoice => invoice.Amount);

// After
var total = context.Invoices.Sum(invoice => invoice.Amount);
```

The diagnostic points to the complete materializer invocation, the same anchor EFD004 and EFD005 use. The evidence names the resolved materializer, the proven `DbSet` origin, and the reducer.

## Supported reducers

| Group | Reducers | Accepted arguments |
|---|---|---|
| Element | `First`, `FirstOrDefault`, `Single`, `SingleOrDefault` | none, or one predicate |
| Ordered element | `Last`, `LastOrDefault` | none, or one predicate; the query must contain `OrderBy` or `OrderByDescending` |
| Existence | `Any` | none, or one predicate |
| Quantifier | `All` | one predicate |
| Count | `Count`, `LongCount`, `List<T>.Count`, array `Length` | none, or one predicate for the methods |
| Aggregate | `Sum`, `Min`, `Max`, `Average` | none over scalar elements (for example after `Select(invoice => invoice.Amount)`), or one property selector |

A predicate is reported only when it uses the same SQL-capable shape EFD004 accepts: entity property paths, constants, captured locals or parameters, null checks, built-in comparisons, and `&&`, `||`, or `!`. A selector must be a direct property path such as `invoice => invoice.Amount`. Reducers with method calls or computed expressions in their lambda (`order.Name.StartsWith("A")`, `order.Total * 2`), comparer or default-value overloads, `Min()`/`Max()` over entities, `Contains`, and `ElementAt` are not reported.

`Last` and `LastOrDefault` are reported only when the query is explicitly ordered, because EF Core cannot translate `Last` over an unordered query.

Static syntax such as `Enumerable.First(Enumerable.ToList(context.Orders))` is reported the same way as reduced syntax.

## Boundaries

Materializers, reducers, and query origins must resolve semantically. The inline source must trace to `DbSet<T>` or `DbContext.Set<TEntity>()`. EFD019 does not report:

- reductions already applied to the query, such as `context.Orders.Count()` or `await context.Orders.FirstAsync()`;
- explicit client-evaluation boundaries such as `AsEnumerable().First()`;
- a materialized list stored in a local and reduced later, because the buffered rows may be reused;
- arbitrary `IQueryable<T>` parameters, in-memory queryables, or in-memory lists;
- a non-awaited async materializer such as `ToListAsync().Result.First()` (EFD011 covers the blocking); or
- look-alike methods named `ToList` or `First` on other types.

## Relationship to EFD004 and EFD005

EFD004 covers `Where`, `Select`, `OrderBy`, `OrderByDescending`, `Skip`, and `Take` immediately after materialization. EFD019 covers the reducers above. The two sets don't overlap, so one materializer gets at most one of those findings. For chains like `ToList().Select(...).First()`, EFD004 reports the first client operator.

EFD005 (unbounded materialization) yields to both rules. When EFD019 applies to a materializer, EFD005 does not also report it, even if EFD019 is suppressed there. EFD005 still reports stored lists and reductions EFD019 cannot classify, such as an unordered `ToList().Last()`.

## Remediation

Apply the reducer to the query before materialization so EF Core translates it into SQL. For an awaited materializer, use the EF Core asynchronous reducer (`FirstAsync`, `CountAsync`, `AnyAsync`, `SumAsync`, and so on). The `List<T>.Count` and array `Length` properties become `Count()` or `CountAsync()`.

Verify semantics in the generated SQL, such as ordering for `First` and string collation for `Min`/`Max`. Keep the materialized list only when its rows are also needed elsewhere; in that case, store it in a variable, which EFD019 does not report.

## Suppression

Use standard Roslyn suppression and record why buffering the full result is acceptable.

```csharp
#pragma warning disable EFD019 // Reviewed: the table holds a handful of configuration rows.
var anyInvoices = context.Invoices.ToList().Any();
#pragma warning restore EFD019
```

For a file or directory scope in `.editorconfig`:

```ini
[EditorConfigSuppressed.cs]
# Reviewed: the settings table holds a handful of rows and the list is cheap to buffer.
dotnet_diagnostic.EFD019.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Performance",
    "EFD019",
    Justification = "The table holds a handful of configuration rows.")]
public static int CountInvoices(SampleContext context) =>
    context.Invoices.ToArray().Length;
```
