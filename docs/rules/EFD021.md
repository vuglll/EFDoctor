# EFD021: DbContext is held in a static field

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD021 when a `static` field's type is, or derives from, `Microsoft.EntityFrameworkCore.DbContext`.

An EF Core `DbContext` is **not thread-safe** and is designed to be short-lived — one instance per unit of work (per request, per operation). A `static` field keeps a single instance alive for the whole process and shares it across every thread and request, which leads to:

- concurrency exceptions such as *"A second operation was started on this context instance before a previous operation completed"*;
- stale reads from the first-level cache, because the context never forgets entities it has already loaded; and
- unbounded memory growth as the change tracker accumulates every tracked entity for the life of the process.

## Reported shape

```csharp
// Before: one shared, process-lifetime context.
public static class Db
{
    public static AppDbContext Context = new();
}

// After: resolve a context per unit of work (scoped DI shown).
public sealed class OrderService(AppDbContext context)
{
    public Task<Order?> FindAsync(int id) => context.Orders.FindAsync(id).AsTask();
}
```

The diagnostic points to the field declaration. The evidence names the field and its resolved `DbContext`-derived type.

## Boundaries

The field type must resolve to EF Core `DbContext` or a derived type. EFD021 does not report:

- an **instance** field, which is scoped to its containing object (the normal injected pattern);
- a `const` field or a compiler-synthesized field;
- a `static` field whose type is not a `DbContext`; or
- a same-named `DbContext` type that does not derive from EF Core's `DbContext`.

A `DbContext` held by a dependency-injection **singleton** (a long-lived instance with no `static` field) is out of scope for this version — detecting it requires DI-registration analysis. A `static` auto-property is the same defect but is also out of scope for now; a computed `static` property that returns a fresh context each call is safe.

## Remediation

Resolve a `DbContext` per unit of work instead of storing one statically:

- register it with a **scoped** lifetime in dependency injection and inject it where needed;
- inject an `IDbContextFactory<T>` and create (and dispose) a context per operation; or
- create the context in a `using` block for a short, well-scoped task.

If the field is genuinely single-threaded and short-lived by construction (for example a small single-threaded console tool that disposes the context on exit), suppress it with a recorded reason.

## Suppression

Use standard Roslyn suppression and record why static state is acceptable.

```csharp
#pragma warning disable EFD021 // Reviewed: single-threaded console tool that disposes the context on exit.
public static AppDbContext Context = null!;
#pragma warning restore EFD021
```

For a file or directory scope in `.editorconfig`:

```ini
[EditorConfigSuppressed.cs]
# Reviewed: single-threaded console tool that disposes the context on exit.
dotnet_diagnostic.EFD021.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Reliability",
    "EFD021",
    Justification = "Single-threaded console tool that disposes the context on exit.")]
public static AppDbContext Context = null!;
```
