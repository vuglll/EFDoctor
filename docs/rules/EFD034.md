# EFD034: EnsureCreated on a context that uses migrations

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD034 when `Database.EnsureCreated()` or `EnsureCreatedAsync()` is called on a `DbContext` type that the same project manages with migrations.

`EnsureCreated` builds the schema straight from the current model, and it records no migration history. Mixed with migrations, it goes wrong in one of two ways:

- **On a new database:** `EnsureCreated` creates the tables but no `__EFMigrationsHistory`. A later `Migrate()` then tries to create the same tables and fails.
- **On an existing database:** `EnsureCreated` does nothing at all, so the migrations added since are never applied by the code that was meant to set the database up.

EF Core's documentation warns against using the two together.

## Reported shapes

```csharp
// Migrations/20260101000000_Initial.cs
[DbContext(typeof(ShopContext))]
[Migration("20260101000000_Initial")]
public partial class Initial : Migration { ... }

// Startup: reported, because ShopContext has migrations.
context.Database.EnsureCreated();

// After: apply the migrations instead.
context.Database.Migrate();
```

A context type counts as migrated when any of these is in the analyzed project:

- a `Migration` class attributed `[DbContext(typeof(T))]`;
- a `ModelSnapshot` class with that attribute;
- a call to `Database.Migrate()` or `MigrateAsync()` on a context of that type.

A context type derived from `T` counts too. The diagnostic points to the `EnsureCreated` call. The evidence names the migration, snapshot, or `Migrate` call that shows the context uses migrations.

## Boundaries

EFD034 doesn't report:

- `EnsureCreated` on a context type with no migrations in the project, such as a SQLite cache context next to a migrated main context;
- a project with no migration classes and no `Migrate` call, including one whose migrations live in another assembly and are applied by a different project;
- a provider switch, where `EnsureCreated` is in one arm of an `if`/`else` or a conditional expression and the other arm calls `Migrate` or `MigrateAsync` on the same context type, as in `if (db.Database.IsSqlite()) … EnsureCreatedAsync(); else … MigrateAsync();`. A switch whose other arm migrates through a helper method is still reported;
- `EnsureDeleted`, `CanConnect`, and other `DatabaseFacade` methods;
- a same-named method that isn't EF Core's;
- test projects, which every rule skips by default.

EFD034 is reported when analysis of the whole project completes. In some IDEs it appears only with full-solution analysis on. Builds and the `efdoctor` CLI always report it.

## Remediation

- Call `context.Database.Migrate()` or `await context.Database.MigrateAsync()` at startup. Or, preferably for production, apply migrations at deployment with a migration bundle or a generated SQL script.
- Keep `EnsureCreated` for contexts without migrations, such as test databases or in-memory caches.

## Suppression

Suppress only for a throwaway database that is recreated every time, such as a local demo, and record why.

```csharp
[SuppressMessage("Correctness", "EFD034", Justification = "Local demo database, recreated on every run.")]
static void CreateDemoDatabase(ShopContext context) => context.Database.EnsureCreated();
```

`#pragma warning disable EFD034` and `dotnet_diagnostic.EFD034.severity = none` in `.editorconfig` also work.
