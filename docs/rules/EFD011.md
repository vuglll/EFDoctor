# EFD011: Synchronous blocking on an EF Core async operation

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD011 when semantic analysis proves that `.Result`, parameterless `.Wait()`, or `.GetAwaiter().GetResult()` directly blocks on a supported EF Core asynchronous operation. Blocking keeps the calling thread occupied while database I/O is pending, reduces scalability, and can contribute to thread-pool starvation or a context-dependent deadlock. The finding identifies a code shape; it does not claim that a production failure or slowdown was measured.

## Reported shapes

```csharp
var customers = context.Customers.ToListAsync().Result;
context.SaveChangesAsync().Wait();
var customer = context.Customers.FindAsync(id).GetAwaiter().GetResult();
var count = context.Customers.CountAsync()
    .ConfigureAwait(false)
    .GetAwaiter()
    .GetResult();
```

The diagnostic spans the complete blocking expression and evidence names both the resolved EF Core operation and blocking API.

## Semantic and expression boundaries

The asynchronous source must resolve to an EF Core query terminal on `EntityFrameworkQueryableExtensions`, `DbContext.SaveChangesAsync` (including an override), or `DbSet<TEntity>.FindAsync`. The consumer must resolve to the BCL task, value-task, or awaiter member. Matching method names in source text is not enough.

The first version follows only a direct expression chain, with parentheses, implicit conversions, and `ConfigureAwait(bool)` allowed. It does not follow a task through a local, field, property, parameter, return value, or helper:

```csharp
var pending = context.Customers.ToListAsync();
UseSynchronously(pending.Result); // Not reported by the first version.
```

Ordinary `await`, returning or composing the task, unrelated async methods, dynamic calls, and `Wait` overloads with a timeout or cancellation token do not report.

## Remediation

Await the operation and propagate async through the caller:

```csharp
var customers = await context.Customers.ToListAsync(cancellationToken);
await context.SaveChangesAsync(cancellationToken);
```

If a genuinely synchronous integration boundary cannot be changed, isolate it, document why it exists, and review its threading behavior. Moving the same wait into another blocking wrapper does not remove the risk.

## Suppression

Use standard Roslyn suppression and record why the synchronous boundary is required.

```csharp
#pragma warning disable EFD011 // Reviewed: legacy host exposes only a synchronous callback.
var customer = context.Customers.FindAsync(id).GetAwaiter().GetResult();
#pragma warning restore EFD011
```

For a file or directory scope in `.editorconfig`:

```ini
[LegacyAdapter.cs]
# Reviewed: legacy host exposes only a synchronous callback.
dotnet_diagnostic.EFD011.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Performance",
    "EFD011",
    Justification = "Legacy host exposes only a synchronous callback.")]
Customer Load(CustomerContext context, int id) =>
    context.Customers.FindAsync(id).GetAwaiter().GetResult();
```
