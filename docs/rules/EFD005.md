# EFD005: Query materialization has no recognized row bound

**Default severity:** Warning; advisory findings render as Info

**Confidence:** High, Medium, or Advisory from the recognized bound and call-site context

EFDoctor reports EFD005 when semantic analysis proves that an inline EF Core query is
materialized with `ToList` or `ToListAsync` and finds no strong row bound.

A query without a recognized strong bound may transfer and buffer more rows than
expected and increase database work, memory use, or latency. EFD005 cannot know the
table size, filter selectivity, workload, or whether every row is required, so this
is a qualified review signal rather than a claim that the code is incorrect.

## Reported forms

```csharp
var allCustomers = context.Customers.ToList();

var activeCustomers = await context.Customers
    .Where(customer => customer.Active)
    .OrderBy(customer => customer.Name)
    .ToListAsync(cancellationToken);
```

`Where` by itself, projection, ordering, `Distinct`, `Skip`, `Include`, and
tracking modifiers do not establish a maximum result count. `AsSplitQuery`,
`AsSingleQuery`, `AsNoTracking`, `AsNoTrackingWithIdentityResolution`,
`AsTracking`, `IgnoreQueryFilters`, `IgnoreAutoIncludes`, `Include`,
`ThenInclude`, `TagWith`, and `TagWithCallSite` are bound-neutral: adding or
removing one never changes the EFD005 outcome.

Evidence identifies the resolved materializer, proven `DbSet` origin, inline
operations, and recognized bound kind and strength.

## Recognized bounds

Strong bounds suppress EFD005:

```csharp
var page = await context.Customers
    .OrderBy(customer => customer.Id)
    .Skip(offset)
    .Take(pageSize)
    .ToListAsync(cancellationToken);

var children = await context.Children
    .Where(child => parentIds.Contains(child.ParentId))
    .ToListAsync(cancellationToken);
```

Strong forms are a resolved query-side `Take`, membership in a local, parameter,
or field collection via `Contains` or `Any`, and equality on a key proven from
available PK, FK, or index metadata.

A key is proven in three ways:

- **Data annotations:** `[Key]`, `[ForeignKey]`, or a unique single-column `[Index]`.
- **Fluent configuration in the same project**, in `OnModelCreating` or an
  `IEntityTypeConfiguration<T>`. The recognized calls are a single-column `HasKey`,
  `HasAlternateKey`, or `HasForeignKey`, or `HasIndex(...).IsUnique()`, in lambda or
  string form. Configuration on a base entity type applies to derived types.
- **EF Core's foreign-key convention:** a property named `<Navigation>Id` next to a
  reference navigation named `<Navigation>`, for example `OrganizationId` next to
  `Organization`. This works even when the configuration lives in another project.

Some things never prove a key:

- composite keys, composite foreign keys, and non-unique or composite indexes;
- configuration in a referenced assembly, or in a migration snapshot that names
  entity types by string;
- a property named `Id` or `<Entity>Id` on its own. A composite key configured out
  of sight can't be ruled out, so such equality stays a name match.

The value compared against the key may be any single value external to the
filtered entity — a constant, a local, a parameter, a field, or a property of
another object such as `child.ParentId == parent.Id` or
`sa.ProductId == product.ProductId`. The comparand being a property access does
not change whether the bound is recognized or its strength; strength is decided
solely by the entity-side key. A comparison between two properties of the filtered
entity itself (`x.A == x.B`) does not bound the query to a single row and is not a
key-equality bound.

Equality can be written with the built-in `==` or with a type's own `==` operator.
That covers `Guid`, `DateTimeOffset`, and their nullable forms. It can also be
written as `.Equals()` in either direction, for example `x.Id.Equals(id)` or
`id.Equals(x.Id)`. Every form is recognized at the same strength. The same applies
to the equality inside `ids.Any(id => id == x.ParentId)`.

Equality on an `Id`, `<Entity>Id`, or `*Id` property proven only by name is a
medium bound. It reports at Advisory confidence and Info severity. Such a query
most likely loads one row, or the children of one known parent, so the finding
stays visible without counting as a warning. A date/time comparison such as
`CreatedUtc >= since` is a weak intent signal and also reports at Advisory
confidence and Info severity.

An otherwise unbounded query in a handler, controller, or service over an entity not
recognized as a small lookup reports at High confidence. Unknown context defaults to
Medium rather than over-claiming.

## Semantic and expression boundaries

Calls must resolve to `System.Linq.Enumerable.ToList` or EF Core
`EntityFrameworkQueryableExtensions.ToListAsync`. The inline source must trace
through resolved `Queryable` and explicitly recognized EF composition to
`DbSet<T>` or `DbContext.Set<TEntity>()`.

EFD005 does not cross `AsEnumerable`, `AsAsyncEnumerable`, or another client
boundary. It follows a query stored in a local only when the local's value at the
materializer is statically determined (see [query locals](README.md#query-locals)). The query is then analyzed as if
it were written inline, and the evidence names the local:

```csharp
var query = context.Customers.Where(customer => customer.Active);
query = query.OrderBy(customer => customer.Name);
return query.ToList(); // Reported: the chain is Where -> local 'query' -> OrderBy -> local 'query'.
```

It does not follow a local reassigned conditionally, such as `if (x) query = query.Take(10);`,
because the bound at the materializer then depends on the path taken. Nor does it follow
query values stored in fields, properties, parameters, return values, or helpers. That
proof boundary is independent of bound-neutral tokens. `ToArray` and other
materializers are outside EFD005. When EFD004 applies to the same materializer,
EFD004 takes precedence and EFD005 does not duplicate it. Likewise, when the
buffered result is immediately reduced with a reducer that
[EFD019](EFD019.md) supports, such as `ToList().First()` or
`(await query.ToListAsync()).Count`, EFD019 takes precedence.

## Remediation and legitimate exceptions

If the result set can grow without bound and every row is not needed, consider
server-side paging with stable ordering, chunked processing, or a purpose-built
aggregate. If every matching row is required—for example, hydrating children for a
known set of parents—full materialization is expected.

Exports, batch processing, migrations, cache warm-up, and known-small lookup tables
are also legitimate. Preserve required semantics and suppress with a recorded reason.

## Test projects and suppression

Findings in projects marked `IsTestProject` or referencing a recognized test
framework remain reported, but the CLI downgrades them to Advisory confidence and
Info severity. They still produce the findings-present exit code.

```csharp
#pragma warning disable EFD005 // Reviewed: intentional full export.
var exportRows = await context.Customers.ToListAsync(cancellationToken);
#pragma warning restore EFD005
```

[ReferenceDataCache.cs]

[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Performance",
    "EFD005",
    Justification = "Known-small lookup table is intentionally cached in full.")]

    context.Set<Country>().ToList();
