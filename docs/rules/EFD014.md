# EFD014: Pagination has no deterministic order

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD014 when semantic analysis proves that an EF Core query pages with `Skip` (optionally followed by `Take`) but has no ordering operator (`OrderBy`, `OrderByDescending`, `ThenBy`, or `ThenByDescending`) earlier in the same inline chain.

Without an explicit order, the database is free to return rows in any order, and that order can change between executions (after inserts, updates, statistics changes, or a parallel plan). Paging over an undefined order means page 2 can repeat rows already shown on page 1 or skip rows entirely. This is a correctness bug, not only a performance concern.

## Reported shapes

```csharp
// Before: skipping rows with no defined order.
var page = context.Orders.Skip(50).Take(25).ToList();

// After: a stable order makes paging deterministic.
var page = context.Orders.OrderBy(order => order.Id).Skip(50).Take(25).ToList();
```

The diagnostic points to the paging operator invocation. For `Skip(...).Take(...)` it anchors on the outer `Take` and emits a single finding. The evidence names the resolved paging operator, the proven `DbSet` origin, the observed inline operators, and the absence of an ordering operator.

## Why Skip and not a bare Take

EFD014 requires `Skip`. Skipping rows is only meaningful over a defined order, so `Skip` without ordering is an unambiguous paging bug. A bare `Take` (top-N) with no ordering — `context.Orders.Take(25)` — is frequently intentional (a sample, a batch read, "give me any N"), so it is **not** reported. Requiring `Skip` keeps false positives near zero. Findings from test projects are downgraded centrally.

## Boundaries

Paging and ordering operators must resolve to `System.Linq.Queryable`, and the inline source must trace to `DbSet<T>` or `DbContext.Set<TEntity>()`. EFD014 does not report:

- a query that applies an ordering operator before `Skip`/`Take` (any recognized ordering suppresses the finding; EFD014 does not judge whether the ordering key is unique);
- `Skip`/`Take` over an in-memory sequence or an arbitrary `IQueryable<T>` parameter whose origin is not a proven `DbSet`;
- a query composed across statements through an `IQueryable` local whose value isn't statically determined, such as one ordered only inside an `if` (see [query locals](README.md#query-locals)); or
- look-alike methods named `Skip`, `Take`, or `OrderBy` on other types.

An ordering applied *after* the paging operator (for example `Skip(n).OrderBy(...)`) does not make paging deterministic and is still reported.

## Remediation

Add a stable ordering before `Skip`/`Take`, typically `OrderBy` on a unique key or a key with a deterministic tie-breaker:

```csharp
context.Orders.OrderBy(order => order.CreatedUtc).ThenBy(order => order.Id).Skip(50).Take(25);
```

An intentionally unordered sample (for example a cheap "give me any N" over a small table) is legitimate; suppress it with a recorded reason.

## Suppression

Use standard Roslyn suppression and record why an undefined order is acceptable.

```csharp
#pragma warning disable EFD014 // Reviewed: intentional unordered sample over a small table.
var sample = context.Orders.Skip(50).Take(25).ToList();
#pragma warning restore EFD014
```

For a file or directory scope in `.editorconfig`:

```ini
[EditorConfigSuppressed.cs]
# Reviewed: intentional unordered sample; ordering is applied downstream.
dotnet_diagnostic.EFD014.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Correctness",
    "EFD014",
    Justification = "Intentional unordered sample for a smoke test.")]
public static List<Order> Sample(SampleContext context) =>
    context.Orders.Skip(50).Take(25).ToList();
```
