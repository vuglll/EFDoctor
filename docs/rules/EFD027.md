# EFD027: Concurrent operations on one DbContext

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD027 when an EF Core asynchronous operation starts while another operation on the **same `DbContext` instance** is provably still pending. The operations are asynchronous query terminals and bulk operations, `SaveChangesAsync`, and `FindAsync`.

A `DbContext` isn't thread-safe and supports one operation at a time. When a second operation starts before the first completes, EF Core throws `InvalidOperationException` ("A second operation was started on this context instance before a previous operation completed"). Whether it throws depends on timing. Against a fast local database, the first query may finish before the second starts, so the bug passes tests and appears under production latency.

## Reported shapes

**Operations passed together to a task combinator.** Arguments are evaluated in order, so every operation after the first starts while the earlier ones are pending:

```csharp
// Reported: AnyAsync starts while CountAsync is still running on the same context.
await Task.WhenAll(context.Orders.CountAsync(), context.Customers.AnyAsync());
```

**An operation started while a task local is unobserved:**

```csharp
var orders = context.Orders.CountAsync();
var customers = await context.Customers.CountAsync(); // Reported: orders may still be running.
return await orders + customers;
```

**Operations projected into a task combinator.** Each selector call starts an operation on the context captured from outside the selector:

```csharp
// Reported: FindAsync starts for every id while the earlier lookups are pending.
await Task.WhenAll(ids.Select(async id => await context.Orders.FindAsync(id)));
```

The `Select` may be passed directly, through `ToList()` or `ToArray()`, or through a local whose value is statically determined. `Task.WhenAny` is handled like `Task.WhenAll`. Array and collection-expression arguments count like a `params` list.

The diagnostic spans the operation that starts while another is pending. Evidence names the resolved operation, the shared context, and either the pending operation or task local, or the captured context.

## Same context instance

Two operations are compared only when their context is proven to be the same instance by symbol. The context is found from the operation's receiver, or from the query's `DbSet` or `Set<T>()` origin. It must be one of these:

- a local that is never written after its declaration, including `using var` and `await using var`;
- a parameter that is never assigned, including primary-constructor parameters;
- a field or auto-property of `this`, or a static one;
- `this`, inside a `DbContext` subclass.

A context reached through a property with a custom getter, a method call, a reassigned local, or another object's member is never compared. Two contexts from two `IDbContextFactory.CreateDbContext()` calls are different instances.

## Boundaries

EFD027 doesn't report:

- operations awaited one after another;
- a task local that is referenced before the next operation. Awaiting it, passing it to a method, or storing it may observe completion;
- a later operation that exists only inside a lambda or local function, which may run later;
- a selector that creates its own context;
- a combinator that holds only one EF operation, the rest being unrelated tasks;
- look-alike `WhenAll`, `WhenAny`, `Select`, or EF method names on other types.

EFD027 doesn't yet cover:

- a synchronous EF call, such as `ToList()`, made while a task is pending;
- `Parallel.For`, `Parallel.ForEach`, `Parallel.ForEachAsync`, and `Task.Run` bodies that capture a context;
- tasks added to a list inside a loop and awaited together later;
- two different symbols that alias the same context instance;
- operations started inside helper methods.

A `Select` over a sequence that happens to hold a single element never overlaps. EFD027 can't know the sequence length and still reports it, because the code is wrong as soon as there are two.

Findings from test projects are downgraded centrally.

## Remediation

Await each operation before starting the next one on the same context:

```csharp
var orders = await context.Orders.CountAsync();
var customers = await context.Customers.AnyAsync();
```

When the work must run concurrently, give each concurrent operation its own context:

```csharp
await using var first = factory.CreateDbContext();
await using var second = factory.CreateDbContext();
await Task.WhenAll(first.Orders.CountAsync(), second.Customers.AnyAsync());
```

## Suppression

Use standard Roslyn suppression, and record why the operations can't overlap.

```csharp
#pragma warning disable EFD027 // Reviewed: the context in this test is a thread-safe double.
await Task.WhenAll(context.Orders.CountAsync(), context.Customers.AnyAsync());
#pragma warning restore EFD027
```

For a file or directory scope in `.editorconfig`:

```ini
[EditorConfigSuppressed.cs]
# Reviewed: the context in this file is a thread-safe test double.
dotnet_diagnostic.EFD027.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Reliability",
    "EFD027",
    Justification = "The context in this test is a thread-safe double.")]
public Task AttributeSuppressed() =>
    Task.WhenAll(context.Orders.CountAsync(), context.Customers.AnyAsync());
```
