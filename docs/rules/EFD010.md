# EFD010: Synchronous database call in an async method

**Default severity:** Warning

**Confidence:** Medium

EFDoctor reports EFD010 when a synchronous EF Core database call is made inside an `async` method or `async` lambda and a direct EF async counterpart exists.

Calling the synchronous API blocks the calling thread for the entire database round trip instead of releasing it with `await`. On a server this holds thread-pool threads under load and undermines the scalability the async pipeline is meant to provide — and the awaitable version is usually one method name away.

## Reported shapes

```csharp
// Before: blocks the thread inside an async method.
public async Task<List<Order>> GetAsync(AppDbContext db) =>
    db.Orders.Where(o => o.Active).ToList();

// After: releases the thread during the round trip.
public async Task<List<Order>> GetAsync(AppDbContext db) =>
    await db.Orders.Where(o => o.Active).ToListAsync();
```

```csharp
// Also reported: SaveChanges and Find in an async method.
await using var tx = ...;
db.SaveChanges();          // -> await db.SaveChangesAsync();
var order = db.Orders.Find(id); // -> await db.Orders.FindAsync(id);
```

The diagnostic points to the synchronous call and names the specific `*Async` replacement.

## Recognized calls

| Call | Async counterpart |
|---|---|
| `ToList`, `ToArray`, `ToDictionary` | `ToListAsync`, `ToArrayAsync`, `ToDictionaryAsync` |
| `First`, `FirstOrDefault`, `Single`, `SingleOrDefault`, `Last`, `LastOrDefault` | the matching `*Async` |
| `Count`, `LongCount`, `Any`, `All` | the matching `*Async` |
| `Min`, `Max`, `Sum`, `Average`, `Contains`, `ElementAt`, `ElementAtOrDefault` | the matching `*Async` |
| `DbContext.SaveChanges` | `SaveChangesAsync` |
| `DbSet.Find` | `FindAsync` |

LINQ terminals are recognized only when their source traces to a `DbSet` (a real database query); `SaveChanges`/`Find` are recognized on a `DbContext`/`DbSet` receiver.

## Boundaries

EFD010 does not report:

- a call in a method or lambda that is not `async` — awaiting is not available without restructuring, so a plain synchronous method is left alone (a future variant may cover `Task`-returning methods without the `async` keyword);
- a call that is already the `*Async` counterpart;
- a terminal over an in-memory sequence or an arbitrary `IQueryable<T>` not proven to originate from a `DbSet`;
- a synchronous call inside a synchronous lambda nested in an async method (you cannot await there); or
- the synchronous arm of an explicit sync/async switch. That is a call in one arm of a `?:` or `if`/`else` whose other arm already awaits the same EF counterpart, with or without `ConfigureAwait`:

  ```csharp
  var setting = async
      ? await settings.FirstOrDefaultAsync(x => x.Name == key)
      : settings.FirstOrDefault(x => x.Name == key); // not reported
  ```

  If the other arm awaits something unrelated, the synchronous call is still reported.

## Relationship to EFD011

EFD011 flags blocking on an async call (`.Result`, `.Wait()`, `.GetAwaiter().GetResult()`). EFD010 flags the opposite mistake — choosing the synchronous API while in an async context. They are complementary and do not double-report.

## Remediation

Await the EF async counterpart named in the finding. A synchronous call is acceptable off the hot request path (startup seeding, migrations, single-threaded tools); suppress those with a recorded reason.

## Suppression

Use standard Roslyn suppression and record why the synchronous call is acceptable.

```csharp
#pragma warning disable EFD010 // Reviewed: startup seeding runs off the request path.
var count = context.Orders.Count();
#pragma warning restore EFD010
```

For a file or directory scope in `.editorconfig`:

```ini
[EditorConfigSuppressed.cs]
# Reviewed: startup seeding runs off the request path.
dotnet_diagnostic.EFD010.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Performance",
    "EFD010",
    Justification = "Startup seeding runs off the request path.")]
public static async Task<int> Seed(SampleContext context)
{
    var count = context.Orders.Count();
    await Task.CompletedTask;
    return count;
}
```
