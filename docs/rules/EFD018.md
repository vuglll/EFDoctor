# EFD018: Unawaited EF Core async operation

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD018 when semantic analysis proves that the task returned by an EF Core asynchronous operation is discarded instead of being awaited or otherwise observed.

A discarded EF Core task runs as fire-and-forget. The save or query may not finish before the `DbContext` is reused or disposed, its exceptions are never observed, and a later operation on the same context can overlap it. `DbContext` is not thread-safe, so the overlap can fail with a concurrent-use error or lose data. The exact outcome depends on timing, so the bug often surfaces only under load.

## Reported shapes

```csharp
// Standalone statement, in an async or a synchronous method
context.SaveChangesAsync();

// Explicit discard assignment
_ = context.Entries.Where(entry => entry.Archived).ExecuteDeleteAsync();

// ConfigureAwait does not await the task
context.SaveChangesAsync().ConfigureAwait(false);

// Null-conditional access
context?.SaveChangesAsync();

// Expression-bodied lambda converted to a void-returning delegate
items.ForEach(item => context.Entities.AddAsync(item));
```

The diagnostic covers the complete discarded expression, including `ConfigureAwait(...)` or the `_ =` assignment. The evidence names the resolved EF Core operation and the discard form: a standalone statement, an explicit discard assignment, or the body of a void-returning lambda. Each discarded expression produces its own finding.

## Supported operations

Operations must resolve to EF Core symbols. Methods from other libraries with the same names are never reported.

- asynchronous `EntityFrameworkQueryableExtensions` operations, including query terminals such as `ToListAsync`, `FirstAsync`, and `AnyAsync`, and the bulk operations `ExecuteUpdateAsync` and `ExecuteDeleteAsync`;
- `DbContext.SaveChangesAsync`, including overrides on derived contexts;
- `DbSet<T>.FindAsync`;
- `AddAsync` and `AddRangeAsync` on `DbContext` and `DbSet<T>`; and
- relational `Database.ExecuteSql*Async` operations such as `ExecuteSqlRawAsync`, when the project references EF Core's relational assembly.

Static extension syntax such as `EntityFrameworkQueryableExtensions.FirstAsync(context.Entities)` is reported the same way as reduced syntax.

## Observed tasks are not reported

EFD018 reports only when the task is directly discarded. It does not report when the task is:

- awaited, including `await context.SaveChangesAsync().ConfigureAwait(false)`;
- returned, including from an expression-bodied lambda converted to a task-returning delegate such as `Func<Task<int>>`;
- stored in a local, field, or property;
- passed to another method, such as `Task.WhenAll` or a helper;
- composed with a continuation such as `ContinueWith`; or
- synchronously blocked with `.Result`, `.Wait()`, or `.GetAwaiter().GetResult()`. [EFD011](EFD011.md) reports those, and the two rules never report the same expression.

EFD018 does not track tasks through locals or helpers to prove they are eventually awaited, and it doesn't cover `async void` methods, transaction APIs such as `BeginTransactionAsync`, or `DbConnection` operations.

## Relationship to CS4014

Inside an `async` method, the C# compiler already warns with CS4014 when a call's task is not awaited. EFD018 overlaps with that warning but adds EF-specific evidence and remediation. It also covers the cases CS4014 misses: synchronous methods, explicit `_ =` discards (which silence CS4014), and void-returning lambdas.

## Remediation

Await the EF Core operation and propagate async through the caller:

```csharp
public static async Task SaveAsync(SampleContext context, AuditEntry entry)
{
    context.Entries.Add(entry);
    await context.SaveChangesAsync();
}
```

If the work really must run in the background, don't discard a task that uses the request's context. Run it on a separately scoped context, for example one created from `IDbContextFactory<TContext>` or a new dependency-injection scope, and observe the task so failures are logged.

## Suppression

Use standard Roslyn suppression and record why discarding the task is safe.

```csharp
#pragma warning disable EFD018 // Reviewed: best-effort audit write on a dedicated, separately scoped context.
_ = context.SaveChangesAsync();
#pragma warning restore EFD018
```

For a file or directory scope in `.editorconfig`:

```ini
[EditorConfigSuppressed.cs]
# Reviewed: best-effort audit write on a dedicated, separately scoped context.
dotnet_diagnostic.EFD018.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Correctness",
    "EFD018",
    Justification = "Best-effort audit write on a dedicated, separately scoped context.")]
public static void WriteAudit(SampleContext context) =>
    _ = context.SaveChangesAsync();
```
