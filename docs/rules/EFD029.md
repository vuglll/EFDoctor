# EFD029: OrderBy discards an earlier ordering

**Default severity:** Warning

**Confidence:** High

EFDoctor reports EFD029 when an EF Core query that is already ordered gets a second `OrderBy` or `OrderByDescending` in the same inline chain. The query must be proven to come from a `DbSet<T>` or `DbContext.Set<TEntity>()`. `OrderBy` starts a new primary ordering. When EF Core translates it, the earlier ordering is dropped, and the SQL sorts by the last key alone.

`OrderBy(a).OrderBy(b)` reads as "by `a`, then by `b`", but the query sorts by `b` only. Rows that tie on `b` come back in an order the database doesn't guarantee, and that order can change between executions. Paging built on the sort can then repeat or skip rows. The code compiles, the results look plausible, and the bug is easy to miss in review.

## Reported shapes

```csharp
// Before: the second OrderBy replaces the first, so orders are sorted by date only.
context.Orders.OrderBy(order => order.Customer).OrderBy(order => order.CreatedUtc);

// After: ThenBy adds a secondary sort.
context.Orders.OrderBy(order => order.Customer).ThenBy(order => order.CreatedUtc);
```

An existing `ThenBy` is discarded along with the `OrderBy` it continues:

```csharp
// Reported: the evidence names both discarded operators, OrderBy -> ThenBy.
context.Orders
    .OrderBy(order => order.Customer).ThenBy(order => order.Id)
    .Where(order => order.Id > 0).AsNoTracking()
    .OrderByDescending(order => order.CreatedUtc);
```

Between the two orderings, EFD029 looks through these operators, none of which can give the first ordering a purpose:

- `Where`;
- `Include`, `ThenInclude`, `AsNoTracking`, `AsNoTrackingWithIdentityResolution`, `AsTracking`, `IgnoreAutoIncludes`, `IgnoreQueryFilters`, `TagWith`, and `TagWithCallSite`;
- `AsSplitQuery` and `AsSingleQuery`.

The diagnostic spans the replacing call, from the `OrderBy` name to its closing parenthesis. With static syntax, `Queryable.OrderBy(source, key)`, it spans the whole invocation. Every replacing call is reported once, so `OrderBy(a).OrderBy(b).OrderBy(c)` produces two findings. The evidence names the resolved method, the proven `DbSet` origin, and the discarded operators in source order.

## Boundaries

Ordering operators must resolve to `System.Linq.Queryable`. EFD029 doesn't report:

- `OrderBy(...).ThenBy(...)`, the correct combined sort;
- a second ordering after `Skip` or `Take`. In `OrderBy(a).Take(10).OrderBy(b)`, the first ordering picks which ten rows are kept, and re-sorting them is legitimate;
- a second ordering after `Distinct`, `Select`, `GroupBy`, a join, a set operation, or any other operator not listed above;
- an earlier ordering that reaches the second one through a local variable, a parameter, a field, or a helper method. The common pattern `IQueryable<T> q = set.OrderBy(defaultKey); if (sortByDate) q = q.OrderBy(...)` overrides a default on purpose. The part of the query *before* the first ordering may still pass through a local (see [query locals](README.md#query-locals));
- ordering over an in-memory sequence, including after `AsEnumerable()` or `ToList()`. LINQ-to-Objects `OrderBy` is a stable sort, which is a different idiom;
- an `IQueryable<T>` whose origin isn't a proven `DbSet`, and look-alike methods named `OrderBy` on other types.

Findings from test projects are downgraded centrally.

## Remediation

If both keys were meant, replace the reported `OrderBy` with `ThenBy`, or `OrderByDescending` with `ThenByDescending`:

```csharp
context.Orders.OrderBy(order => order.Customer).ThenByDescending(order => order.CreatedUtc);
```

If replacing the earlier ordering was intended, delete the earlier ordering so the query says what it does.

## Suppression

Use standard Roslyn suppression, and record why the replacement is intended.

```csharp
#pragma warning disable EFD029 // Reviewed: the override is intended.
var orders = context.Orders.OrderBy(order => order.Customer).OrderBy(order => order.CreatedUtc);
#pragma warning restore EFD029
```

For a file or directory scope in `.editorconfig`:

```ini
[EditorConfigSuppressed.cs]
# Reviewed: the default ordering is overridden on purpose.
dotnet_diagnostic.EFD029.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Correctness",
    "EFD029",
    Justification = "The override is intended.")]
public static IQueryable<Order> Sample(SampleContext context) =>
    context.Orders.OrderBy(order => order.Customer).OrderBy(order => order.CreatedUtc);
```
