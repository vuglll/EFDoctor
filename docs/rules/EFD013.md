# EFD013: Load-loop-save pattern may support a bulk operation

**Default severity:** Warning

**Confidence:** Medium

EFDoctor reports EFD013 when semantic analysis proves a narrow EF Core load/loop/save shape that may be replaceable by `ExecuteUpdate`, `ExecuteUpdateAsync`, `ExecuteDelete`, or `ExecuteDeleteAsync`. The rule identifies an opportunity for review; it does not claim that a bulk operation is behaviorally equivalent or that runtime cost has been measured.

## Reported update shape

The query must be materialized, the resulting sequence must be consumed by a `foreach` that performs only uniform direct scalar-property assignments, and the same context must save immediately afterward:

```csharp
var rows = context.Entities
    .Where(entity => entity.Id > 0)
    .Take(100)
    .ToList();

foreach (var entity in rows)
{
    entity.Status = status;
    entity.Active = false;
}

context.SaveChanges();
```

Constants, parameters, defaults, and stable local or field values are eligible. Multiple property assignments produce one finding for the complete operation chain. Synchronous `ToList`/`ToArray` and awaited `ToListAsync`/`ToArrayAsync` forms are supported.

## Reported delete shape

The loop may instead contain exactly one resolved `DbContext.Remove(entity)` or matching `DbSet.Remove(entity)` call:

```csharp
var rows = await context.Entities
    .Where(entity => entity.Id > 0)
    .Take(100)
    .ToListAsync();

foreach (var entity in rows)
{
    context.Remove(entity);
}

await context.SaveChangesAsync();
```

The diagnostic spans the materialization expression. Its evidence names the resolved materializer, query origin, uniform property assignments or delete operation, and matching save method.

## Non-triggering forms

EFD013 stays silent when a bulk replacement cannot be established conservatively. Examples include:

- the assigned value reads the current entity, such as `entity.Status = entity.Status + 1`;
- the loop branches, calls another method, logs, emits events, changes unrelated state, contains nested control flow, or mixes update and delete behavior;
- a target is nested, navigation-like, computed, indexed, incremented, or compound-assigned;
- `SaveChanges` occurs inside the loop, after an intervening statement, or on another context;
- the sequence is reassigned, used before the loop, passed by reference, escaped, or obtained through ambiguous control flow;
- a method merely has the same name as an EF Core API;
- the target project's EF Core references do not expose the corresponding bulk operation.

`SaveChanges` inside a loop remains the separate EFD001 concern. EFD013 also does not cover `RemoveRange`, disconnected-entity workflows, conditional per-row changes, arbitrary batching, or interprocedural query flow.

## Likely impact

Loading rows before a uniform update or delete can transfer data that is not needed by the application, allocate and track entity instances, run change detection, and generate per-row modification commands. The actual cost depends on the number of rows, provider, mappings, batching, indexes, and transaction behavior.

## Remediation and semantic cautions

Review whether the original query can invoke the matching bulk operation directly:

```csharp
await context.Entities
    .Where(entity => entity.Id > 0)
    .Take(100)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(entity => entity.Status, status)
        .SetProperty(entity => entity.Active, false));
```

Do not treat this as a mechanical rewrite. EF Core bulk operations execute immediately and bypass tracked-entity state and the normal `SaveChanges` pipeline. Before changing the code, verify:

- provider translation and entity/table-mapping support;
- optimistic-concurrency and concurrency-token handling;
- `SaveChanges` interceptors, overrides, domain callbacks, and audit behavior;
- delete cascades and other relationship behavior;
- transaction boundaries and partial-failure expectations;
- whether matching entities are already tracked and would become stale. [EFD038](EFD038.md) reports that shape when the load and the bulk operation are in one method.

Retain the tracked loop when those semantics are intentional or when the bulk operation cannot express the required behavior safely.

## Precision boundaries

The first version performs same-body, symbol-based analysis rather than whole-program alias or control-flow inference. It accepts a direct materialized loop source or a local with one proven initializer and no intervening use or write. The query must trace to a `DbSet` property or `DbContext.Set<T>`, and the save receiver must resolve to the same owning context. These restrictions intentionally trade recall for lower false-positive risk.

## Suppression

Use standard Roslyn suppression only after reviewing and documenting why tracked `SaveChanges` semantics are required.

```csharp
#pragma warning disable EFD013 // Reviewed: tracked audit callbacks are required.
var rows = context.Entities.Where(entity => entity.Id > 0).Take(100).ToList();
foreach (var entity in rows)
{
    entity.Active = false;
}
context.SaveChanges();
#pragma warning restore EFD013
```

For a file or directory scope in `.editorconfig`:

```ini
[TrackedBulkWorkflow.cs]
# Reviewed: SaveChanges interceptors produce required audit records.
dotnet_diagnostic.EFD013.severity = none
```

Where the Roslyn host supports it:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage(
    "Performance",
    "EFD013",
    Justification = "Tracked domain callbacks are required for every entity.")]
void UpdateWithTrackedCallbacks(SampleContext context)
{
    var rows = context.Entities.Where(entity => entity.Id > 0).Take(100).ToList();
    foreach (var entity in rows)
    {
        entity.Active = false;
    }
    context.SaveChanges();
}
```
